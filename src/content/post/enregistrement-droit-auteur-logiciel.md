Un logiciel s'enregistre auprès du Copyright Office en tant qu'œuvre littéraire, la même catégorie qu'un roman, et l'enregistrement protège le code tel qu'il est écrit : la séquence précise des instructions, la structure et les commentaires, sous forme de code source comme de code objet. Ce qu'il ne protège pas, ce sont les fonctionnalités. Un concurrent qui écrit un nouveau code faisant la même chose ne contrefait pas votre droit d'auteur (copyright), et c'est pourquoi le droit d'auteur d'un logiciel constitue une couche de protection et non une stratégie complète. Dans cette limite, l'enregistrement est peu coûteux, rapide, et il représente la seule voie vers les dommages-intérêts légaux (statutory damages) et le remboursement des honoraires d'avocat contre quelqu'un qui copie le code lui-même. Notre [pratique en enregistrement des droits d'auteur](/fr/practice-area/key-services/copyright-registration) dépose des enregistrements de logiciels pour des startups comme pour des entreprises établies, et les questions ci-dessous se posent dans chaque dossier.

## Ce que couvre l'enregistrement du droit d'auteur d'un logiciel

Le droit d'auteur protège l'expression, pas les idées, les systèmes ni les méthodes de fonctionnement. Pour les logiciels, les tribunaux distinguent l'expression protégeable des éléments non protégeables : l'algorithme, les fonctions dictées par un souci d'efficacité ou par des contraintes externes, les techniques de programmation courantes et tout ce qui provient du domaine public ou de bibliothèques open source. Ce qui reste, à savoir les choix propres au programmeur dans la manière d'écrire et d'organiser le code, est protégé.

L'enregistrement d'un programme informatique peut aussi couvrir les affichages à l'écran et l'interface utilisateur que génère le programme, si la demande décrit la revendication de manière à les inclure. Les éléments audiovisuels d'un jeu et le code sous-jacent peuvent être enregistrés ensemble ou séparément, selon la façon dont la création est décrite. L'essentiel est de décrire la création dans la demande avec les termes que l'Office reconnaît (« computer program » et, le cas échéant, « text » et « artwork ») plutôt qu'avec un vocabulaire marketing.

## Les exigences de dépôt et le problème du secret des affaires

C'est sur la copie de dépôt que les logiciels se distinguent des autres œuvres. La circulaire actuelle de l'Office sur les programmes informatiques demande le code source plutôt que le code objet ; pour un programme de plus de cinquante pages, le dépôt standard comprend les vingt-cinq premières et les vingt-cinq dernières pages, y compris la page portant la mention de réserve du droit d'auteur s'il y en a une. Les programmes plus courts sont déposés dans leur intégralité.

Beaucoup de sociétés ne veulent pas voir cinquante pages de code source figurer dans un registre public. L'Office prévoit des solutions de rechange pour les programmes contenant des secrets des affaires. À la date de rédaction, le demandeur peut déposer les vingt-cinq premières et les vingt-cinq dernières pages en occultant les parties relevant du secret des affaires, à condition que les parties occultées soient proportionnellement moins importantes que le contenu laissé visible et que ce contenu visible fasse apparaître une expression protégeable ; ou les dix premières et les dix dernières pages du code source sans aucune occultation ; ou les vingt-cinq premières et les vingt-cinq dernières pages du code objet accompagnées d'au moins dix pages consécutives de code source sans occultation. La demande doit indiquer que la copie de dépôt contient des éléments relevant du secret des affaires. Choisir entre ces options relève d'une appréciation de la part sensible du code et de ce qui doit rester visible pour établir la création, et nous faisons ce choix avec le client avant le téléversement.

Un demandeur qui souhaite déposer uniquement du code objet peut le faire en vertu de la « règle du doute » (rule of doubt) de l'Office, accompagné d'une lettre confirmant que le contenu comporte une création protégeable. Le certificat obtenu porte alors une mention indiquant que l'Office n'a pas pu vérifier la revendication, ce qui affaiblit la présomption de validité en cas de contentieux. Pour un code qui constitue un véritable secret des affaires, la meilleure voie est souvent un dépôt de code source occulté, associé aux politiques décrites sur notre page consacrée à la [protection du secret des affaires](/fr/practice-area/key-services/trade-secret-protection).

## Versions et œuvres dérivées

Chaque version publiée d'un programme constitue une œuvre distincte aux fins de l'enregistrement. Un enregistrement couvre le code tel qu'il existait dans la copie de dépôt ; l'enregistrement de la version 1.0 ne s'étend donc pas aux éléments nouveaux ajoutés dans la version 2.0. Si la version 1.0 a été enregistrée, la demande pour la 2.0 doit exclure la version antérieure dans la section de limitation de la revendication et décrire les éléments nouveaux. Si la version 1.0 a été publiée mais jamais enregistrée, il s'agit d'un contenu déjà publié que la demande pour la 2.0 doit également exclure ; la solution la plus propre consiste donc à enregistrer d'abord la 1.0 séparément.

En pratique, il convient d'enregistrer aux étapes de publication significatives plutôt qu'à chaque commit : une version majeure, une version qui introduit le code le plus susceptible d'être copié, ou une version qui sera concédée sous licence à des clients. Les règles de dépôt applicables aux programmes révisés permettent de déposer les parties révisées lorsque les révisions ne figurent pas dans les vingt-cinq premières et dernières pages. Les sociétés qui livrent en continu doivent choisir un rythme (trimestriel, ou à chaque version majeure) et s'y tenir.

## Open source et code de tiers

Les bibliothèques et frameworks open source ainsi que tous les composants de tiers sous licence doivent être exclus de la revendication. C'est dans la section de limitation de la revendication que vous identifiez ces éléments, en termes généraux, comme des œuvres préexistantes dont le titulaire revendiquant n'est pas propriétaire. Revendiquer trop en incluant une bibliothèque dans un enregistrement ne vous confère aucun droit sur celle-ci et donne au défendeur une raison d'attaquer le certificat. Une nomenclature logicielle (bill of materials) à jour de la base de code, que les investisseurs demanderont de toute façon, simplifie cette section.

## La titularité avant le dépôt

La demande désigne l'auteur et le titulaire revendiquant (claimant). Le code écrit par des salariés dans le cadre de leurs fonctions est un travail à la commande (work made for hire), et la société en est l'auteur. Le code écrit par un prestataire appartient à ce prestataire, sauf si une cession signée le transfère ; une clause de travail à la commande seule ne fonctionne généralement pas pour un logiciel, car le logiciel ne fait pas partie des catégories légales qui permettent de traiter l'œuvre d'un prestataire comme un travail à la commande. La différence est expliquée dans notre article sur [le travail à la commande et la cession de droits d'auteur](/fr/work-for-hire-ou-cession-droits-auteur). Réunissez les cessions avant le dépôt afin que le certificat indique correctement la titularité.

## Droit d'auteur, brevet ou secret pour un même code

Le droit d'auteur est la protection par défaut et devrait presque toujours être obtenu. Ajouter un brevet pour une méthode technique nouvelle, ou garder plutôt un algorithme comme secret des affaires, est une décision distincte qui implique d'autres arbitrages. Notre article sur [le choix entre secret des affaires et brevet](/fr/secret-des-affaires-ou-brevet) en expose les critères. Les trois peuvent coexister : le droit d'auteur pour le code tel qu'il est écrit, le secret des affaires pour les parties occultées et les mécanismes internes non publiés, et un brevet, lorsque c'est possible, pour la méthode.
